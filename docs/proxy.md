# 网络代理 · 设计说明

`dsh-net-proxy` 让 **DSH 自身进程**的出站 HTTP(S) 走代理。
本插件**不向会话写入任何内容**。

本文记录实现为什么长这样，尤其是几个无法从代码表面看出来的约束。

## 标识

| 项 | 值 |
| --- | --- |
| 包名 | `dsh-net-proxy` |
| Host 插件名 | `netProxy` |
| 浏览器半边 locale 命名空间 | `netProxy` |
| Host 路由 | `/net-proxy/state` |
| 设置文件 | profile 目录下的 `net-proxy.json` |
| 凭据引用 | `DSH_NET_PROXY_PASSWORD` |
| 设置页 | Settings → 网络代理（`settings.section` id `net-proxy`） |

## 一句话结论

生效通道是 `node:http.setGlobalProxyFromEnv()`，喂给它的是一个**合成环境对象**，
不是 `process.env`。这一条同时解决了「覆盖哪些网络栈」和「密码不泄漏」两个问题。

## 为什么是它

Host 进程的出站请求会走两条完全不同的栈：

| 栈 | 谁在用 | 手工装 undici dispatcher 能覆盖吗 |
| --- | --- | --- |
| undici 全局 dispatcher | `fetch`：模型 API、`web_fetch`、HTTP MCP | 能 |
| `http(s).globalAgent` | 自己构造 `http.request` 的 SDK | **不能** |

`setGlobalProxyFromEnv()` 装的是**两个**：既调用 `setGlobalDispatcher(new EnvHttpProxyAgent(...))`，
也替换 `http.globalAgent` 与 `https.globalAgent`。实测两条路径都会经过代理：

```
fetch('https://…')          -> 代理收到 CONNECT host:443
http.get('http://…')        -> 代理收到 absolute-form GET http://…
https.get('https://…')      -> 代理收到 CONNECT host:443
```

而它返回的 `restore()` 正好就是 Cordis effect 需要的 disposer 形状。

## 为什么密码不进 `process.env`

函数签名是 `setGlobalProxyFromEnv(env = process.env)` —— 它接受**任意对象**。
所以这里传的是一个新建的普通对象：

```js
http.setGlobalProxyFromEnv({ http_proxy: 'http://alice:p%40ss@host:8080', https_proxy: '…', no_proxy: '…' })
```

实测：装完之后 `process.env` 里一个代理变量都没有，而请求照常带
`Proxy-Authorization: Basic …`。这比「先写 `process.env`、装完再删掉」更安全 ——
后者依赖删除时机，而前者从一开始就没有写进去。

意义在于：shell 工具 fork 子进程时子进程继承 `process.env`。密码若在里面，
模型跑一条 `env` 就能看见。现在它只活在 `EnvHttpProxyAgent` 的闭包里。

## 分层：启动层 → 本插件 → restore

`dsh-http-proxy` 在启动时已经按用户自己的 `http_proxy` / `ALL_PROXY` 装过一层。
本插件是**叠在它上面**的第二层：

```
启动层 (launcher)          <- installGlobalProxy(policy)
   ↑ restore() 回到这里
本插件 (this plugin)       <- setGlobalProxyFromEnv(synthetic env)
```

关掉插件 = 调 `restore()` = 回到启动层，而不是回到裸进程。用户自己的代理配置不会被抹掉。

实测：叠第二层后 `restore()`，路由回到启动层的策略；再次安装又回到插件策略，可反复切换。

### 「直连」不是「什么都不做」

如果启动层已经装了策略，那么「不安装」不等于「直连」—— 启动层的代理还在生效。
所以 `mode: direct`（以及启用但没解析出代理时）会装一个 **`no_proxy: '*'`** 的 agent：

```js
{ no_proxy: '*', http_proxy: 'http://127.0.0.1:1', https_proxy: 'http://127.0.0.1:1' }
```

`127.0.0.1:1` 是保留端口，永远不会被拨号；它只是让 transport 有东西可装。
`*` 让所有请求绕过，于是覆盖了下层的策略，同时仍然可以 `restore()` 回去。

## 回环地址必须强制并入

原生匹配器**不会**自动绕过 loopback（实测：裸 `127.0.0.1` 目标会被送进代理）。
如果不强制并入，DSH 自己的 Web UI（`127.0.0.1:63736`）和 Connection 传输会被塞进代理，
形成路由回环。

所以 `localhost, 127.0.0.1, ::1, [::1]` 四项**永远**出现在有效绕过列表里，不可关闭。
`::1` 和 `[::1]` 都要写，因为 undici 会把裸 `::1` 读成 host `:` port `1`。

## 绕过列表：能表达什么、不能表达什么

原生匹配器的规则（实测，不是推测）：

| 写法 | 行为 |
| --- | --- |
| `*` | 全部绕过 |
| `example.com` | 精确匹配 + 所有子域 |
| `.example.com` / `*.example.com` | 同上 |
| `host:port` | 限定端口 |
| `10.*` / `192.168.*` | **不匹配** |
| `<local>` | **不匹配** |
| CIDR (`10.0.0.0/8`) | **不匹配** |

后三种是 Windows `ProxyOverride` 常见的写法，但 Node 的匹配器没有「部分标签通配」
和「无点主机名」的概念。本插件**不会**把它们悄悄传下去 —— 那样会看起来生效、
实际仍走代理。它们被丢弃，并在设置页明确写出来：

> 跳过列表中的「10.*」无法由 Node 的代理规则表达，已忽略。

`127.*` 同样被丢弃并报告，因为 `LOOPBACK_NO_PROXY` 只覆盖 `127.0.0.1` 这一个地址，
不是整个 `127/8`。

## 为什么没有 `Config`

插件所在的目录常常在 profile 的依赖树之外（安装时链接或复制进来）。实测在这个位置：

```
undici                   -> MODULE_NOT_FOUND
@deepseek-ai/schemastery -> MODULE_NOT_FOUND
@deepseek-ai/dsh-tools   -> MODULE_NOT_FOUND
```

（经 profile 符号链接解析也一样。）而 `export const Config` 需要 schemastery。

所以 Host 半边**只用 Node 内置模块**，设置存到 profile 目录下的
`net-proxy.json`，由插件自己的 RPC 通道读写。好处是零依赖、可手改；
代价是不会出现在插件管理器自动生成的配置表单里 —— 设置页由本插件自己提供。

写入是原子的：新内容先落到 `.tmp`，再 `rename` 覆盖。半个文件会被下次启动读成损坏。

## 密码存在哪里

| 位置 | 内容 |
| --- | --- |
| `net-proxy.json` | 只有 `authUser`，永远没有密码 |
| DSH 凭据库 | 密码，键为 `DSH_NET_PROXY_PASSWORD` |
| `process.env` | 什么都没有 |
| 路由返回值 | `http://***@host:port`（`redactUrl` 的结果） |
| 会话 | 没有任何写入 |

浏览器半边**不直接调用 `ctx.remote.credentials`**，而是通过插件自己的同源路由
（`endpoint: 'secret'`）让 Host 代为读写：

- `describe` 只能回答「是否已配置 / 是否可写」，读不回值；
- `set` 只收非空密码，且要求设置里已有用户名（Basic 认证缺一半等于没有认证）；
- `unset` 之后**立刻重新 describe**，因为删掉已存值可能让环境变量里的回退值重新生效，
  直接报「未配置」就是谎报。

为什么不用 `ctx.remote.credentials`：那是**生成的 Remote 命名空间**，只有客户端半边显式声明
`remote` 服务才挂得上来。一个「只负责一块设置表单」的插件，不该因为客户端未来调整
Remote 的挂载方式就丢掉整段认证配置。既有路由已经过宿主自己的登录/Host 闸门、仅同源可写，
用它可以让密码和配置只走一条通道、只在一处鉴权。

顺带一个必须说清的两阶段语义：**存密码不等于生效**。凭据库和路由是两次独立写入，
只有再点一次「保存并应用」才会把新凭据装进 transport。界面因此有 `auth.pending`
（凭据库已更新、路由未应用）和 `auth.partial`（密码写成功但配置应用失败）两个状态——
这两种情况既不谎报成功，也不谎称凭据被回滚。

## 客户端怎么和 Host 说话（这一条踩过大坑）

第一版用了 `connection.rpc.handle`。它在浏览器半边**永远拿不到**：

- 静态加载的客户端半边跑在一个沙箱里，只提供 `fetch`、`ctx`、`React`、`styles`；
- 它没有模块加载器，所以**看不到 `connection` 服务**，`ctx.get('connection')` 返回
  `undefined`，`connection.rpc` 也就是 `undefined`；
- 结果是设置块渲染成空壳，而且**不报任何错** —— 界面上就显示「没有设置项」。

（`connection.rpc.handle` 服务的是另一类调用方；`host.call` / `harness.handle` 那套属于
「动态插件」，即从控制台粘贴代码创建的那种，本地 profile 里的包用不到。）

正确的通道是 **`webServer.register` 一个 exact 路由 + 客户端 `fetch`**。
宿主自带的几个 Web 插件也是这么做的，`/net-proxy/state` 就是这条路径。

安全上有两道闩，因为 exact 路由会在 `/api` 统一闩**之前**被匹配，不经过它：

1. `connection.requestRejection(request)` —— 宿主自己的 Host/Origin 检查与浏览器登录校验，
   和它的 API 走同一套。**按请求读**：`connection` 服务在异步初始化之后才构造，
   本插件挂载时它还不存在。
2. 自己的 loopback 兜底 —— 宿主老到没有 `connection` 时用 `Host` 头判断
   （`Host` 是恶意页面唯一伪造不了的请求头）。实测 `127.0.0.1` / `localhost` / `[::1]`
   放行，`evil.example.com` 与 `127.0.0.1.evil.com` 都是 403。

路由还做了三件事：只接受 POST、请求体上限 64 KiB、所有回复 `cache-control: no-store`。

## 设置界面的信息结构

界面长这样，是因为代理配置有三个容易混淆的地方，布局必须把它们分开：

1. **「正在编辑的」和「正在生效的」不是一回事。** 改任何**配置字段**都只进草稿，底部标
   「有未保存的修改」，只有「保存并应用」才会真正切换路由。这样「我关了代理」和
   「代理其实还开着」不会看错。
   **「启用代理」这个开关是唯一的例外**（见下条）。
2. **启用开关不归「保存并应用」管。** 它拨动即生效：客户端自己发一次 save，载荷是
   *当前草稿*加新的开关值，成功后用 Host 回复的已生效值定位开关。理由是这个开关回答的是
   「此刻走不走代理」，一个一秒内就该有答案的问题，不是一份要编辑再提交的文档。把它放进
   草稿的代价很具体：用户拨了开关，底部却显示「有未保存的修改」——那句话描述的是**表单**，
   不是用户刚刚要求的**路由**，于是他还得再点一次保存才能让自己刚才那一下生效。

   随之而来三条必须守住的边界：

   - **脏标记不认这个开关。** 只有开关变化不算「有未保存的修改」；否则每拨一次都会点亮
     提交行，而那个按钮对此无能为力。
   - **打开之前先本地校验。** 提交带的是当前草稿，所以一个没保存的坏地址会跟着上去，然后
     被 Host 以「地址无效」拒绝——报的还是一个用户当时没在看的字段。所以**打开**前先在
     本地校验并指到那个字段；**关闭永远不校验、不阻塞**，否则一个坏草稿会把用户困在他正
     想退出的代理状态里。
   - **失败要回弹。** 开关先乐观移动，Host 拒绝时退回已生效值并给出 `error.toggle`。
     开关不能停在一个 Host 没接受的位置上。
3. **认证是一次独立的写入，但必须和配置一起生效。** 密码走凭据库，配置走设置文件；
   两者是两个事务。所以密码不会自己「自动生效」，而是和草稿共用同一个「保存并应用」，
   并在失败时区分「密码已写入但配置没应用」（`auth.partial`）—— 这种情况既不谎报成功，
   也不谎称凭据被回滚。
4. **没有「刷新」按钮，保存后自动重读。** 保存成功后客户端会自己再读一次 Host 状态，
   只读区域（系统代理报告、绕过列表的生效值、探针结果）因此总是描述**实际生效**的配置。
   这次重读失败时保持静默：保存已经成功，为一次后续读取弹错误只会让人以为保存失败了。
   重读期间用户如果又改了草稿，新草稿保留，只有状态被刷新。
5. **「测试」测的是表单当前的草稿。** 选中的来源、填的地址、绕过列表——测的就是这些，
   不必先保存。这一点是刻意的：用户要判断的是**他正准备提交的配置**能不能用，而不是
   上一次保存的东西。所以草稿有改动时按钮依然可用。

   实现上，Host 会拿草稿解析出策略，**临时装上**、发两次请求、再还原。走真实传输层而不是
   自建 agent，因为自建 agent 会在真实请求失败时照样显示成功（测了一个用户根本不会经历的
   路径）。还原精确回到上一层，测完进程状态与测前一致。

   **延迟取第二次请求。** 第一次请求要付 DNS、TCP 握手、TLS 协商的代价——实测同一目标
   冷启动 784 ms、复用会话后 219 ms。那个数字描述的是冷启动成本，不是代理的开销，而它恰好
   是用户每次点「测试」都会看到的数字。所以先发一次预热（不计时），再发一次计时。预热还
   兼一份活：路径不通时它在预热就失败，直接返回，不会把失败粉饰成一个很快的结果。计时
   起点紧贴计时那次请求，安装传输层与预热的耗时都不混进来。

   结论只有两个词：**测试通过** / **测试失败**，通过时带上延迟。跟着保存行状态句，用 `·` 分隔。

   判定标准是「请求完成且返回的不是错误」。4xx/5xx 算失败——有东西应答了但拒绝了，
   这条路不通；把它记成通过（早先那种「已连通」写法就是这么干的）等于在代理刚转发失败时
   告诉用户配置可用。

   **延迟只在通过时显示。** 那是换一个来源重测的理由，也是短而等宽的内容，不会扰动行高。
   失败时不显示：超时那一次的 3007 ms 量的是超时本身，不是链路。

   其余信息全部进紧跟在后的圆形 `i` 图标浮窗，行内一律不显示：

   | 情况 | 行内 | 浮窗 |
   | --- | --- | --- |
   | 经代理通过 | 测试通过 · 224 ms | — |
   | 直连通过 | 测试通过 · 30 ms | 直连，未经过代理 |
   | 目标返回 4xx/5xx | 测试失败 | 目标返回 HTTP 502 |
   | 请求未完成 | 测试失败 | 原始错误文本 |

   这么切分是因为那句话坐在按钮旁边：耗时、状态码、错误栈都是变长内容，一旦进场就会
   把保存行撑成两行、把按钮挤走。状态句自身强制单行、超出省略，行高因此恒定。浮窗文字
   同时用作 `aria-label`，不悬停也能被读屏读出。

版面上沿用了 DSH 设置页本身那套排版——**行 + 发丝线**，而不是自成一体的卡片盒子：

| 区域 | 内容 | 为什么在这 |
| --- | --- | --- |
| 上下文缓存 | 一段说明：切换开关会让当前对话的缓存失效一次 | 开在**页面最上面**。它说的是这个开关的代价，所以必须在伸手去拨之前读到；放在表单末尾等于用户已经改完才告诉他 |
| 启用代理 | 一行开关：控制 DSH 软件自身的网络请求是否走代理 | 本插件唯一的开关；关闭时保留 DSH 原有网络设置 |
| 代理来源 | 28px 分段控件（五个来源）+ 所选来源的一句话说明 | `direct` 与「关闭」是两件不同的事，必须能区分 |
| 地址 | 自定义/自动来源才出现的地址输入 | 与所选来源无关的输入框不再灰着占位；一个地址同时用于 http 与 https 目标 |
| 代理认证 | 带标题的一组字段：用户名、密码、清除已存密码 | 标题行左侧带一句「密码只写入凭据库」，右侧标出凭据状态 |
| 高级设置 | 带标题的一组字段：绕过列表（始终显示当前生效值，来源自有时只读）、测试地址 | 全部平铺可滚动，不需要点开才看得到 |
| 保存行 | 状态句（含测试结果）+ 「还原修改」+「测试」+ 倒色「保存并应用」 | 一次提交，紧跟在它要提交的内容后面 |

只读诊断不再占一整块「运行信息」：取消该栏后，Host 报告的绕过规则被丢弃、设置文件
损坏、SOCKS5 实验特性等**可操作警告**仍以紧凑列表显示在表单最上方；正常状态不出现。

排除地址框直接填入当前生效的绕过列表：来源自带列表（系统代理、环境变量）时只读，
自定义来源空值时填入生效值，有草稿时显示草稿并在下方标出生效值。

自定义来源只有**一个**地址，它同时用于 http 与 https 目标。策略对象里仍然分开的
`httpProxy` / `httpsProxy` 不是给用户填的：系统代理的 `ProxyServer` 与环境变量本来
就可能给出两个不同的值，传输层需要分别接住，所以这两个字段属于**解析结果**，不属于设置。

两组都是**平铺**的，没有任何折叠控件。分组只用一条发丝线和一行标题表达：标题在左，
该组当前状态在右（「密码已保存」「按需配置」），正文始终展开。理由很直接——
用户点开这一页通常是为了改某一个字段，把字段藏在一次点击后面只是多加一步，还得让用户
猜哪个组里有什么。页面本来就只有一列滚动，全部展开不会让目标更难找。

开在最上面的「上下文缓存」组是个例外：它**没有顶部发丝线**（`data-leading`）。发丝线的
作用是分隔，而它上面什么都没有；更重要的是，它读起来应当像是紧随其后的那个开关的注解，
而不是一个独立章节——中间画一条线，反而把「代价」和「拨动它的动作」切成了两件事。

组内沿用同一套行与字段节奏：标题行下方直接是字段，由标题行承担与上一组的分隔。

标题行除了组名与状态，还可以带**一句说明**（目前只有「代理认证」用）。这句说明是关于整组
的，所以放在标题行、读字段之前；放在最后一个字段下面，用户往往已经填完了才看到。窄容器下
这句话换到自己一行，而不是压缩成省略号——被省略的恰好是「密码去哪了」这个关键信息。

字段之间的发丝线由「上方是否还有字段」决定，而不是由 `:first-child` 决定。这个区别在
两列网格里会漏：网格的每个格子都自成一个 `:first-child`，于是标题行下面会多出一条通栏
横线。所以规则写成显式的两条——栈里的第一个字段不画线，网格里的字段一律不画线。

具体的排版取值来自对已发布 GUI 的实测，不是自创：

- 开关 36×20、滑块 16、位移 16px；分段控件 28px 页签 + 4px 轨道 + 滑动指示块；
- 输入框 34px 高、`--dsw-radius-md`、`border-l4` 发丝线、`bg-layer-3`；
- 行标题 14/22、行描述 12/18；行分隔线用 `border-l2`，最后一行去掉；
- 焦点用 `--dsw-alias-state-business-primary`（不是品牌色）；输入框聚焦换边框而不是画光圈；
- 提交按钮用倒色（`label-primary` 底 + `bg-layer-3` 字），不是品牌色填充；
- 状态只用颜色 + 文字成对出现，圆点从不单独承载含义。

窄窗口（设置弹窗被拖窄，或 200% 缩放）靠容器查询 `@container npd-proxy (max-width: 520px)`：
分段控件从「五列一行」变成「两列换行」，双列输入并单列，诊断表并单列，按钮占满整行；
`min-width: 0` 与 `minmax(0, 1fr)` 保证长代理地址在任意宽度下换行而不撑破页面。
颜色只用主题 token，因此亮/暗主题自动跟随。

## 对话输入框里的状态胶囊

设置页不是用户待着的地方——他们待在对话里。所以「现在走不走代理」这件事在 composer 的
工具栏里也有一处只读胶囊：一个 6px 圆点 + 「代理已启用 / 代理未启用」，悬停给出当前来源
（`chip.onHint` 里的 `{source}`）或「去设置里开」的指引。

座位选的是 `conversation.input.left`，也就是**完全权限下拉框右边那一格**。composer 工具栏
的排布是「`+` → 权限 → 计划 → `conversation.input.left`」，所以胶囊落在权限控件右侧；
计划模式开启时中间会多一个计划胶囊，胶囊仍然紧跟其后。放在这里而不是
`conversation.input.dock`（composer 上方整行），是因为「这个会话能做什么」和「它的请求从哪出去」
是同一次扫视要回答的两个问题，两行分置等于多一次寻找。

几条约束：

- **只读，不可点。** 没有 hover 底色、没有指针光标、没有焦点环——放一个开关在这儿，
  对话中途误触一次就是一次上下文缓存失效。开关仍然只有设置页那一个。
- **尺寸借的是工具栏的，不是设置页的。** 28px 高、13/20 字、`--dsw-radius-sm`，与旁边的
  权限下拉框同高，否则整行会被这一格顶歪。窄容器（`@container (width<=560px)`）下与宿主
  一起收窄，标签优先省略，把宽度让给真正可操作的控件。
- **样式表挂在 document 上，不挂在设置页里。** 设置页那份 `<style>` 是页面元素的子节点，
  只在设置页挂载时存在——而胶囊恰恰在设置页关闭时才在屏幕上。所以胶囊的规则由 `apply`
  里的一次 `ctx.effect` 装进 `document.head`，卸载时移除。
- **首帧不猜。** 状态还没读到时不画「未启用」——那会是一个假的结论。没读到就不渲染。
- **保存后必须立刻变。** 这一条是补的 bug：胶囊和设置页是**同时挂载**的——关掉设置页
  并不会卸载 composer。早期胶囊只在挂载时读一次、外加标签页重新可见时再读一次，于是
  在设置页关掉代理并保存后，胶囊仍然写着「代理已启用」，直到用户恰好切走再切回标签页。
  现在有一条页面级的共享路由状态（`routeState`）：设置模型每收到一个 status（首次读取、
  保存回复、保存后的重读）就发布一次，胶囊订阅它。谁先知道谁发布，后来挂载的一方直接
  从最新值开始，不再空着。
- **迟到的读取不能覆盖新值。** 胶囊自己也会读一次 status（比如页面直接进对话时），而
  这次读可能比一次保存更早发出、更晚回来。共享状态带一个单调递增的 revision：请求发出时
  记下 revision，回来时若已经变过就丢弃。否则「关掉代理后状态没变」会以更低的概率重现。

## 界面状态机的几个决定

浏览器半边把状态放在一个可观察的小模型里（`createSettingsModel`），而不是散在组件里。
这不是为了架构好看，是因为下面几种情况都会让「表单显示」和「实际配置」脱节：

| 情况 | 处理 |
| --- | --- |
| 语言切换导致 `t` 换身份 | 模型不依赖 `t`，只依赖自己；翻译变化不再重新拉取状态 |
| 保存密码后重新读状态 | 只刷新「已生效」部分，**不覆盖**未保存的草稿 |
| 两个状态请求乱序返回 | 递增序号，旧回复直接丢弃 |
| 组件卸载时请求还在飞 | `AbortController` 取消，迟到回复不写状态 |
| 请求永远不返回 | 18 秒（探针 12 秒）超时，进入可重试的错误态 |
| 连续点两次保存 | 第二个操作被 `busy` 拒绝，且不会重复写密码 |

模型同时是离线回归测试的接缝：`test/verify-client.mjs` 使用假的 Host 与凭据库，
驱动真实状态转换。这类测试能抓住「加载失败后按钮消失」「保存密码吞掉草稿」
「旧探针结果冒充新配置」这类问题，但它**不证明**真实页面长什么样 —— 视觉仍需人眼确认。

## 生效范围（重要）

**只有 Host 进程。** 具体是：

| 会走代理 | 不会走代理 |
| --- | --- |
| 模型 API 调用 | 渲染进程（浏览器窗口自身的请求） |
| `web_fetch` / `web_search` | 系统里其他程序 |
| HTTP 形式的 MCP 服务器 | `ctx.ssh` 连接 |
| 任何用 `fetch` / `http(s).request` 的插件 | 工具子进程（它们的网络请求不经过本进程） |

子进程不走代理是设计而非疏漏：把代理交给子进程意味着要把凭据交给它，而这与「默认不给
模型密码」冲突。子进程确实需要出网时，由用户自己在那条命令里显式指定。

## 已知限制

1. **PAC 不支持。** 注册表里有 `AutoConfigURL` 时会在设置页报警并忽略。
2. **socks5 是实验特性。** Node 会打 `ExperimentalWarning`。`socks5h://` 与 `socks4://` 被明确拒绝
   （原生 transport 只认 `http:`/`https:`/`socks5:`，其余直接抛 `Invalid URL protocol`）。
3. **TLS 中间人**需要用户自己设 `NODE_EXTRA_CA_CERTS`，本插件只做提示。
4. **纯 http 目标会被隧道化**（`CONNECT` 到 80）。个别代理不支持这种形式，此时对 http 目标需直连。
5. **非 Windows 没有系统代理读取**：只会读环境变量。
6. **系统代理只在可能用到时才读。** 读注册表要起一个 `reg.exe` 子进程（本机实测
   52–74 ms），所以 `install()` 先过 `needsSystemProxy()`：插件关闭，或来源被钉在
   `custom`/`env`/`direct` 时，启动完全不读。只有 `auto`（可能落到系统）与
   `system` 会读。设置页在 `system` 来源下仍要显示读取结果，那一份由 status 请求
   懒读并去重，同样不在启动路径上。
7. **老运行时降级**：没有 `setGlobalProxyFromEnv` 时退回 `undici` + `EnvHttpProxyAgent`，
   只覆盖 `fetch`，设置页的「生效范围」会如实显示 `undici（fetch only）`。

## 验证

`node test/run.mjs` 依次跑四个脚本，离线覆盖：

| 脚本 | 覆盖 |
| --- | --- |
| `verify-host.mjs` | 设置归一化（缺字段、错类型、未知键）、代理 URL 校验与凭据处理（编码、脱敏、剥离）、绕过列表翻译、Windows `ProxyServer` 两种写法、解析链（custom → system → env，各自独立不混用）、持久化（往返、损坏容错、不落密码） |
| `verify-route.mjs` | 路由端到端：405/400/未知端点、保存与回滚、凭据单向写入、探针报告真实路线、请求闸门 |
| `verify-client.mjs` | 浏览器半边的注册形状、词典完整性、页面渲染、样式不含硬编码色值，以及输入框胶囊的座位、样式表与首帧行为 |
| `verify-package.mjs` | 清单一致性：package.json、patch、naming 声明、locale 与源码常量互相咬合 |

全部用本地服务器，不访问外网。
